# 持仓校准：CTP 单腿持仓 → 跨期组合持仓的反推依据

本文整理「持仓校准」功能的反推依据（数据来源、字段口径、公式、边界处理），
以及据此实现的校准规则与代码位置。

## 1. 目的与范围

本系统把跨期价差当成一个策略单元（slug 如 `OI611-OI701`），持仓在本地按
**组合维度 + 分层**保存（`Position.side` / `Position.tiers`，价差 = `near − far`）。

而 CTP 只登记**单腿合约持仓**（`OI611`、`OI701` 各自的多/空手数与成本），
组合合约（`SPD OI611&OI701`）本身不在投资者持仓查询里体现。
因此需要用单腿持仓反推组合持仓，再与本地比对/校准。

范围：
- 只读 CTP 持仓，不涉及报单；校准只改**本地记账**，不发单、不撤单；
- 触发方式：网页「⚖ 持仓校准」按钮（先预览 → 确认后应用）+ REST API，不自动执行。

## 2. 数据来源与字段口径

查询接口：
- vnpy 通道：`TdApi.reqQryInvestorPosition`（`onRspQryInvestorPosition` 回调逐行返回）；
- C++ 通道：报单引擎协议 `{"type":"query_position","instrument":<腿>}` → `positions` 行。

返回结构 `CThostFtdcInvestorPositionField`，关键字段与使用口径：

| 字段 | 含义 | 本项目口径 |
|---|---|---|
| `InstrumentID` | 合约代码（腿） | 必须精确等于 `near_leg` / `far_leg` 才纳入反推 |
| `PosiDirection` | 持仓方向：`'2'` 多 / `'3'` 空 / `'1'` 净 | 多→long、空→short；净持仓见 §5.3 |
| `Position` | 总持仓手数（昨仓 + 今仓，含冻结） | 反推手数用它（对账总量口径） |
| `YdPosition` | 上日持仓（昨仓） | 仅作展示/明细，不参与配对 |
| `TodayPosition` | 今仓手数 | 仅作展示/明细 |
| `PositionCost` | 持仓成本（**金额** = Σ 价格 × 乘数 × 手数） | 反推腿均价：`PositionCost ÷ (Position × 乘数)` |
| `OpenCost` | 开仓成本（今仓开仓金额） | 不使用（口径只覆盖今仓，且部分柜台不回填） |
| `LongFrozen` / `ShortFrozen` | 挂单冻结手数 | 不使用：对账看总持仓，挂单在报单侧独立对账 |
| `PositionProfit` | 持仓盈亏 | 不使用 |

同一合约的持仓**按「方向 + 今昨仓」拆成多行**（最多 4 行：多今/多昨/空今/空昨），
因此反推前必须先按 `(合约, 方向)` 汇总。

乘数 `M`：取注册表 `config/contracts.json → contracts.<slug>.multiplier`
（跨期两腿同品种，假设乘数相同；若两腿乘数不同，反推均价不可靠，见 §5.4）。

## 3. 反推公式

记：
- `N_L / N_S`：近月腿多头 / 空头手数；`F_L / F_S`：远月腿多头 / 空头手数（按 §2 汇总后）；
- `P_NL / P_NS / P_FL / P_FS`：对应腿的**腿均价**（元/吨）：
  `P = PositionCost ÷ (Position × M)`（若通道直接给价格均价则直接用该价格）。

组合维度（价差 = 近月 − 远月）：

1. 手数配对（取两腿配对的 min）：
   - 组合多头手数 `C_L = min(N_L, F_S)` —— 近月多 + 远月空 = 做多价差；
   - 组合空头手数 `C_S = min(N_S, F_L)` —— 近月空 + 远月多 = 做空价差。
2. 成本（价差点数）：
   - 组合多头成本 `= P_NL − P_FS`；
   - 组合空头成本 `= P_NS − P_FL`。
3. 净方向（本地模型同一时间只允许单方向）：
   - `C_L > C_S` → `LONG`，手数 `C_L − C_S`，均价取组合多头成本；
   - `C_S > C_L` → `SHORT`，手数 `C_S − C_L`，均价取组合空头成本；
   - `C_L == C_S` → 无净持仓（`C_L = C_S > 0` 属于对锁，见 §5.2）。
4. 未配对部分（`N_L − F_S`、`F_S − N_L` 等）视为**单边裸腿**，不纳入组合手数，
   只告警（见 §5.1）。

示例（OI 类，乘数 10）：

| 腿 | 方向 | 手数 | PositionCost | 腿均价 |
|---|---|---|---|---|
| OI611 | 多 | 3 | 24 000 | 800 |
| OI701 | 空 | 3 | 27 000 | 900 |

→ 组合多头 3 手，组合成本 = 800 − 900 = −100（即价差 −100 点）。

## 4. 与本地模型的口径差异（重要）

1. **盯市成本 ≠ 原始建仓价**：`PositionCost` 的昨仓部分按**上一交易日结算价**重算，
   今仓部分按开仓价。所以反推出的组合成本是「当前持仓的盯市成本」，
   跨过结算日后不等于当初成交的价差。本地 `Tier.avg_price` 是实际建仓价差，
   且 `min_exit_pnl` / 预挂止盈目标价都按它反解。
   → **校准默认不覆盖本地已有均价**，只提示差异（`docs` 与预览中可见）。
2. **今昨仓合并**：校准只关心总量；平今/平昨标志由下单环节处理
   （本系统平仓统一用平仓标志），不在校准范围内。
3. **冻结手数**：`Position` 含冻结，本地持仓不含未成交挂单占用；
   挂单由报单对账（`strategy/reconcile.py`）单独处理。
4. **组合持仓表**：CTP 另有 `ReqQryInvestorPositionCombineDetail`（组合腿明细）。
   本系统不查该表：按用户口径，柜台侧持仓以单腿登记，反推即为组合持仓。
   若某些柜台设置为按组合合约登记，单腿查询会为空 → 校准提示「未查询到腿持仓」
   并且**不清空**本地持仓（fail-safe）。

## 5. 边界情况与处理

### 5.1 残腿（两腿手数不匹配）
`N_L ≠ F_S` 或 `N_S ≠ F_L` 时，多出的一侧是单边裸腿（历史遗留/手工单/其他策略）：
- 组合手数仍取配对的 `min`；
- 告警：`两腿多头手数不匹配：近月 X 手 vs 远月 Y 手，未配对 N 手（单边裸腿，需人工核对）`。

### 5.2 双向持仓（对锁）
`C_L > 0` 且 `C_S > 0`：柜台同时持有多、空两个组合方向，本地模型只支持单方向：
- 按净手数 `|C_L − C_S|` 校准，方向取较大一侧；
- 告警提示柜台双向手数，便于人工决定是否手工拆掉某一侧。

### 5.3 净持仓模式（`PosiDirection = Net`）
部分交易所/柜台设置返回净持仓（`'1'`），此时：
- `Position < 0` → 视为空头，手数取 `|Position|`；
- `Position ≥ 0` → 视为多头；
- 仍按多头/空头两条腿参与反推，并在明细中标记 `direction=net→long/short`。

### 5.4 成本/乘数不可用
- 通道只给价格 `avg_price`（C++ 引擎）时直接用；给的是成本金额时按 §3 换算；
- 两腿乘数不同或未配置（`multiplier <= 0`）→ 均价不可用，只校准方向与手数；
- 换算出的腿均价超出合理区间（> 1e6 元/吨，说明口径不符）→ 视为不可用并告警。

### 5.5 查询失败 / 通道不支持
- 无交易通道、通道不支持单腿持仓查询、查询超时/异常 → 返回错误，**不修改本地持仓**；
- 查询成功但两腿均为空 → 视为柜台无持仓；此时若本地有持仓，校准会**清空本地**
  （属于用户主动确认后的操作，预览里明确列出「清空持仓」）。

## 6. 校准规则（用户确认口径）

1. **均价**：本地已有均价 → 保留；只有本地缺失（空仓或均价为 0）才用 CTP 反推成本补齐。
   CTP 反推价与本地均价的差异在预览中告警（`> tick_size` 时提示）。
2. **层结构**：方向一致时尽量保留
   - 目标手数少于本地 → 从**最新层**（列表尾部）开始削减，削到 0 的层移除；
   - 目标手数多于本地 → 先按已有层的自然手数（`max(1, 现有最大层手数)`）从最新层开始补齐，
     仍有剩余则**新增层**，最多到 `layering.max_positions` 层；
     超过层数上限的部分并入最新层并告警；
   - 方向不同或本地空仓 → 重建为单层（手数 + 均价）。
3. **只改本地记账**：不发单、不撤单、不自动预挂止盈；变更写入决策日志
   （`action=校准`）并落盘 `<sim_|real_>position.json`。

## 7. 共享腿（多合约共用一条腿）与腿总量守恒

### 7.1 场景

一条腿可能同时属于多个跨期组合：`a2701` 既是 `a2611-a2701` 的远月，也是
`a2701-a2703` 的近月。柜台只看到腿持仓，例如 `a2611` 多 1、`a2701` 空 2、`a2703` 多 1
（多 `a2611-a2701` + 空 `a2701-a2703`，两组合都把 `a2701` 当空腿）。

逐合约独立反推时，`a2701` 被另一组合占用的那 1 手会被误判成"单边裸腿"并告警。

### 7.2 账户级联合反推（`allocate_legs`）

- 一次查询**同一实盘通道**所有注册合约涉及的腿（去重；模拟合约不参与，避免扣减实盘腿）；
- 按「**本地有持仓的合约优先**」顺序逐个配对（避免新开仓合约抢走已有持仓的腿），
  每个组合只从**剩余腿手数**里取 `min(近月方向手数, 远月反方向手数)`，配对后扣减剩余；
- 结果：上述场景中 `a2611-a2701` = 多 1 手、`a2701-a2703` = 空 1 手，
  共享的 `a2701` 空 2 手被两个组合各用 1 手，**不再误报裸腿**；
- 分配后仍剩余的腿进入 `unused`，提示"未被任何已注册跨期组合使用（手工单/其他策略）"。

### 7.3 腿总量守恒校验（`leg_conservation`）

把本地各合约持仓展开成腿需求（多头 = 近多 + 远空；空头 = 近空 + 远多），与柜台可用手数比较：

| 情况 | 处理 |
|---|---|
| 需求 ≤ 可用 | 允许校准（多余的腿属于其他策略/手工单，不阻断；`unused` 里提示） |
| 需求 > 可用 | `blocked=true`，**拒绝应用**，告警"可能为净持仓口径抵消，或其他策略/手工单占用" |

为什么需要：共享腿反向时（一个组合要 `a2701` 空、另一个要 `a2701` 多），若柜台把多空
**净额化**（`a2701` 净 0），按剩余腿反推会得到"无持仓" → 直接应用会把本地真实持仓误清。
守恒校验把这类情况挡在应用之前（只预览、不改本地）。

### 7.4 接口与返回字段

`GET/POST /api/position/{slug}/calibrate` 额外返回：

- `allocation`：`inferences`（各合约联合反推）/ `used`（本系统组合占用的腿）/ `unused`（无人使用的腿）/ `order` / `warnings`；
- `conservation`：`ok` / `required` / `available` / `shortfalls`（含原因）；
- `blocked` / `blocked_reason`：守恒不通过时为 `true`，POST 返回 HTTP 200 但 `applied=false`，
  本地持仓不动，前端提示"已拒绝自动校准"。

### 7.5 单合约回退

`engine.calibrate_position_from_ctp` 保留（只配对本合约两腿，不看共享腿），用于无 App
上下文/单测；网页与 API 走账户级版本 `App.calibrate_position`。

## 8. 代码位置

| 位置 | 职责 |
|---|---|
| `strategy/calibration.py` | 纯计算：腿汇总、组合反推、校准计划；`allocate_legs`（共享腿联合反推）/ `leg_conservation`（腿总量守恒） |

| `web/server.py` | `App.calibrate_position`（账户级：联合反推 + 守恒校验 + 应用） |
